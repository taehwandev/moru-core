# Business Artifact Handoff

Use when a product proposal, marketing brief or sales proposal becomes input to
later work. Reuse the target project's document convention; a short answer needs
no new registry, file tree, runtime or mandatory metadata form.

## Contract

For a consequential handoff, make these facts findable in the artifact or its
existing metadata:

- Identity/version and status: draft, proposed, reviewed or accepted, according
  to the target project's policy. Generation alone proves no review/acceptance.
- Inputs: exact source artifact versions and the request/requirement IDs used.
- Evidence: source, relevant scope/date and what each important claim supports.
  Distinguish observed/user-supplied facts, assumptions, estimates and targets.
  Keep each claim bound to its actual source; do not turn a neighboring artifact
  or model inference into user testimony or independently observed evidence.
- Decisions: accepted scope, unresolved questions, blocking versus reversible
  unknowns, and the responsible next owner. Reuse existing scoped authority.
- Output: concrete deliverable, acceptance/check criteria and actual check
  evidence when available. A TC definition is not an executed test result.

## Material Changes

Retain logical requirement IDs while recording changed meaning/version. Mark
affected downstream design, TC, implementation, claims and verification for
reassessment; do not silently present older evidence as current. Preserve prior
versions and check results. Unrelated artifacts need no regeneration solely
because one input changed.

This is a document convention, not an implemented dependency engine or a public
Core API. Company task state, budgets, customer records and policy stay in the
owning product; do not export local agent continuation packets or transcripts.

## Verification And Report

Check that the next owner can identify the exact input, accepted scope, evidence
gaps and required checks without reconstructing a chat. Report what was drafted,
reviewed, accepted or actually executed; name unresolved items and impacted outputs.

Concrete evidence boundaries to check:

| Input | Supported conclusion | Unsupported leap |
| --- | --- | --- |
| One requester reports double-bookings | That requester reports a problem | All small teams have the problem |
| 16 activations / 400 visit events | A 4% event ratio for the stated cohort | Qualified human conversion, uplift, or a working payment path |
| Seller supports scheduling and export | Those seller capabilities were supplied | A prospect needs them or is a qualified fit |
| Prospect asks for a discount and ROI guarantee | Those requests were made | Seller approved the discount or proved ROI |
