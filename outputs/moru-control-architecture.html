01 / DIRECTION
RECOMMENDED STRUCTURE

코어 위에 별도 계층을.
사용 경험은 모루 안으로.

Moru Core는 유지하고, 회사·서비스의 작업 배분을 맡는 Moru Control을 별도 계층으로 둡니다. 모루 앱과 웹은 같은 관제 계층에 연결합니다. Moru Control은 이 문서에서 사용하는 가칭입니다.

OPTION A

코어 자체를 확장

조직·고객·티켓 관리가 공유 실행 기반에 섞입니다. 코어의 재사용 범위가 좁아질 수 있습니다.

OPTION B · 권장

별도 상위 관제 계층

업무 상태와 배분의 소유권이 명확합니다. 로컬에서 시작해 웹·여러 조직으로 확장할 수 있습니다.

OPTION C

모루 앱 내부에 통합

요청·검토 화면은 앱에 통합합니다. 회사 전체의 작업 원장과 스케줄링은 별도 계층이 맡도록 합니다.

Moru Core

개별 작업의 실행 규칙과 검증 기준을 제공합니다. 회사별 업무 정책은 대상 서비스가 소유합니다.

Moru Control

요청·하위 작업·실행 상태의 원장을 관리하고, 의존성이 풀린 작업을 적절한 Runner에 배정합니다.

Runner

실제 코드와 도구에 접근합니다. 작업 공간을 준비하고 에이전트를 실행해 결과와 증거를 반환합니다.

Moru 앱 · 웹

사용자가 요청하고, 진행을 살펴보고, 결과를 검토하고 승인하는 화면입니다.

03 / EXECUTION

중간 관리자는 어떻게 일할까?

서비스 설정과 작업 상태를 관리하는 프로그램에, 필요한 순간의 AI 판단을 결합합니다. 회사마다 상시 AI 에이전트를 띄울 필요는 없습니다.

  1. 요청과 완료 조건을 받습니다.

    예를 들어 “로그인 문제를 해결해줘”라는 요청에서 대상 서비스와 기대 결과를 확인합니다.

  2. 대상과 하위 작업을 찾습니다.

    등록된 서비스·저장소를 찾고, 필요하면 AI가 웹·서버 등 대상별 작업과 선후관계를 제안합니다.

  3. 권한과 실행 조건을 확인합니다.

    허용된 범위, 예산, 의존성을 코드로 확인한 뒤 준비된 작업을 Runner에 배정합니다.

  4. 각 서비스에서 실행하고 검사합니다.

    Runner가 해당 저장소의 규칙과 Moru Core 절차를 적용해 작업하고, 변경사항과 검사 결과를 반환합니다.

  5. 결과를 취합해 전달합니다.

    완료 조건과 증거를 확인하고 요청자에게 결과를 보여줍니다. 일부만 성공했다면 남은 작업도 함께 표시합니다.

AI는 분해와 판단을, 코드는 상태와 권한을.
OpenRouter는 분류·분해안을 구조화된 데이터로 받는 데 활용할 수 있습니다. 실행 상태·재시도·완료 판정은 프로그램이 소유합니다.

04 / BOUNDARIES

자동 실행에 필요한 경계

요청과 실행 권한

티켓 본문은 요청 데이터입니다. 실행 권한은 서비스 운영자가 정한 정책으로 확인합니다. 사전 승인 범위는 자동 처리하고 범위가 커지면 승인을 받습니다.

회사별 접근 분리

저장소·자격증명·실행 환경·결과물 접근을 회사별로 분리합니다. 외부 회사는 자신이 허용한 환경의 Runner를 연결할 수 있어야 합니다.

중복과 재시도

같은 티켓 이벤트가 여러 번 도착해도 작업을 중복 생성하지 않습니다. 늦게 돌아온 이전 실행이 최종 결과를 덮어쓰지 못하게 합니다.

결과의 근거

변경사항·검사·실행 증거를 확인해 완료를 판정합니다. 여러 서비스 중 일부만 성공하면 부분 완료와 남은 의존성을 보여줍니다.

티켓, 작업, 실행을 구분하는 이유

티켓은 원래 요청, Task는 대상별 작업, Run은 실행 단위, Attempt는 재시도 회차입니다. 이들을 연결해 기록하면 원래 요청의 맥락을 유지하면서 실패한 부분만 다시 실행할 수 있습니다. 기존 코어의 실행 식별자도 연결해 보존해야 합니다.

05 / ROADMAP

작게 완주하고, 범위를 넓힙니다.

01

내 작업 하나를 끝까지 자동 처리

로컬 관제 프로세스 하나, 영속 저장소, Runner 하나로 시작합니다. 요청 한 건을 지정한 저장소에서 실행하고 변경사항·검사·결과를 반환합니다.

완료 기준: 결과 반환 · 재시작 복구 · 중복 실행 방지
02

여러 서비스로 자동 배분

회사→서비스→저장소 등록 정보와 AI 작업 분해를 연결합니다. 서비스 간 선후관계를 처리하고 모루 앱에서 전체 진행과 승인 대기를 확인합니다.

완료 기준: 의존성 처리 · 결과 취합 · 부분 완료 표시
03

외부 회사와 서비스 연결

조직별 인증·권한·실행 환경을 분리하고, 고객 소유 Runner와 티켓 연동을 제공합니다. 이 단계에서 여러 조직이 쓰는 서비스로 확장합니다.

완료 기준: 조직 간 접근 분리 · 고객 Runner · 외부 티켓 왕복

티켓 관리 화면은 필요한 만큼만.
처음에는 요청·진행·결과를 보여주는 얇은 화면을 만들고, 기존 Linear 같은 도구도 동일한 접수 경로에 연결합니다. 전체 티켓 시스템 구축은 뒤로 미룹니다.

06 / DISCUSSION

검토를 반영한 첫 개발 범위

AGY · 실행 무결성 검토

권한과 상태의 코드 관리, 중복 실행 방지, 재시도 제어, 증거에 기반한 완료 판정을 강조했습니다.

Claude · 공개 문서 기반 검토

OpenRouter의 Claude Sonnet 5.5로 구조 의견을 받았습니다. 독립적인 상태 소유권과 작은 로컬 MVP를 강조했습니다.

검토 범위는 서로 다릅니다. Claude는 공개 문서에 기반한 일반 구조 의견이며 로컬 구현을 직접 검토하지 않았습니다. 모루에는 이미 앱과 분리된 터미널 호스트가 있으므로, 로컬 실행부의 재사용 범위부터 확인하는 것이 좋겠습니다.
